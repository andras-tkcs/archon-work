# devflow pack for Archon

Issue to pull request, for any repository that has a devflow profile (`.devflow/devflow.yaml`):
`devflow-refine` turns an issue into a design, `devflow-plan` turns the design into a plan and a
build workflow, `build-issue-<n>` implements it unattended and opens one PR, and
`devflow-follow-up` continues or corrects a build on a task. `devflow-init` writes the profile and
the rest of a repository's devflow setup. Five more workflows cover quick edits, docs, security,
repository configuration and Dependabot. The pack holds no project
facts: branch rules, checks, docs to read, changelog and CI come from the profile, and the
project's environment comes from its own SessionStart hook. It needs no Claude Code plugin.

`bootstrap.sh` installs it as an Archon plugin for the agent user, so every project on the runner can
use it. Installed, its workflows are named `<owner>/devflow:<workflow>`, for example
`tkcs-lab/devflow:devflow-refine`.

The repository moved from the `andras-tkcs` org to `tkcs-lab`. A runner bootstrapped before that
still has the pack installed as `andras-tkcs/archon-work/packs/devflow`, with workflows named
`andras-tkcs/devflow:*`. Re-running `bootstrap.sh` installs the pack again under the new source. To
keep one copy, remove the old one with `archon plugin` or set `DEVFLOW_PACK` to the old source.

| Workflow | Use it for | Pauses for a person when |
|---|---|---|
| `devflow-refine` | Turn an issue into `design.md` on the `plans` branch, then plan it, revise it or stop | At most two question rounds (up to 5, then up to 3 questions), each one pause; then one pause: plan, revise or finish |
| `devflow-plan` | Turn a refined issue into `plan.md`, `plan-test.md`, `before.md`, `after.md` and the build workflow `build-issue-<n>` | Never; a gap the design leaves goes to the issue comment as a question for `devflow-refine` |
| `build-issue-<n>` | Generated by `devflow-plan`: implement and test the plan's phases, record every decision in `deviations.md`, review, definition of done, local CI, one PR watched until a person merges it | Never; stuck phases and decisions go to `deviations.md` |
| `devflow-follow-up` | Continue or correct a build (stopped, PR open or merged) on a task given in words | Never |
| `devflow-init` | Write `.devflow/devflow.yaml` and the rest of a repository's devflow setup, through one PR; re-run it whenever a project fact changes | At most two question rounds, only where the scan cannot settle a required key |
| `devflow-quick` | A small edit with no plan (a typo, a one-file fix); refuses anything bigger | Never; it cancels with the reason if the edit is not small |
| `devflow-docs` | Review the docs and the website, fix what is wrong | Never; undecidable items are listed in the PR |
| `devflow-audit` | Security audit, then verify the findings, plan and fix them | The verifier leaves a decision to the maintainer |
| `devflow-config` | Review a repo's rulesets, Actions, access and security settings and workflow files; fix file gaps through a PR and list settings gaps for the admin | Never; settings changes are listed for the admin |
| `devflow-deps` | Repair and push Dependabot PRs; fix vulnerability alerts no PR covers | Never; PRs it cannot fix are handed to a person with the evidence |

Workflows named `mod-*` are building blocks you never start yourself. `mod-devflow-refine-block`
and `mod-devflow-plan-block` are the two stages, `mod-devflow-attention` is the pause after a
stage, and `mod-devflow-trace` writes a build's state to the issue comment. `mod-devflow-tail` is
the shared delivery tail (review, fixes, definition of done, PR, watch), included by
`devflow-quick`, `devflow-docs`, `devflow-config`, `devflow-deps`, `mod-devflow-audit-fix` (which
`devflow-audit` includes) and `mod-devflow-deliver`; it runs the definition of done and local CI
through `mod-devflow-dod`. A generated `build-issue-<n>` starts `mod-devflow-start` (branch and
stub `deviations.md`), `mod-devflow-before-check` (the read-only check of `before.md`),
`mod-devflow-phase` per phase, `mod-devflow-merge` per wave, `mod-devflow-wrap` (deviations.md,
commit, push) and `mod-devflow-deliver`; `devflow-follow-up` includes the same blocks. No workflow
merges.

## Run it

```bash
cd /path/to/a/registered/repo
archon workflow run tkcs-lab/devflow:devflow-init --detach          # once per repository; merge its PR
archon workflow run tkcs-lab/devflow:devflow-refine "#42" --detach
archon workflow run tkcs-lab/devflow:devflow-plan "#42" --detach   # unless you answered "plan" to refine
archon workflow sync
archon workflow run build-issue-42 --detach
archon workflow run tkcs-lab/devflow:devflow-follow-up "#57 rename the flag" --detach   # later, if needed
```

From the web UI or chat, ask for `devflow-refine` with the issue. `--input scope=...` focuses
`devflow-docs` and `devflow-audit`; `--input reference=<owner>/<name>` gives `devflow-config` a
repository whose setup to compare against.

## What a project needs

- `.devflow/devflow.yaml`, the devflow profile (section "Profile" below), written by `devflow-init`.
  It must validate with the pack's `validate-profile.py`, and must have `version: 1`, `verify.fast`
  and `verify.dod`. Without it every workflow stops with
  `.devflow/devflow.yaml not found: run devflow-init first`.
- Optionally, a SessionStart hook in `.claude/settings.json`. The `setup` node runs every SessionStart
  command hook (no matcher, or one that admits `startup`) in the run's worktree with
  `CLAUDE_CODE_REMOTE=true`, `CLAUDE_PROJECT_DIR` and `CLAUDE_ENV_FILE` set, the way a fresh
  Claude Code cloud session would. That is where the project builds its venv, installs
  `node_modules` and so on; what the hook exports through `CLAUDE_ENV_FILE` (a `PATH` with the venv,
  for example) is written to `project-env.sh` in the run's artifacts, which the checks load and the
  agents source before project commands. A hook that exits non-zero fails the run before any
  model is called. Without a hook nothing is installed, and checks whose tools are missing show up
  as `UNAVAILABLE` (definition of done) or red (fast checks).

Before that, `setup` restores full history and tags (`git fetch --unshallow --force --tags`), which
version tools such as `setuptools_scm` need. Origin's tags win: a tag re-pointed upstream replaces
the local one, as in a fresh clone.

## Host requirements

`preflight` checks these before any model is called: a valid profile, `gh` authenticated, and an
`origin` remote. The validators need `python3` with PyYAML; script nodes need `bun`. `bootstrap.sh`
provides all of them. Anything else a project's hook or checks call (`uv`, `node`/`npm`, a
compiler) must be on the host: commands the host cannot run are reported as `UNAVAILABLE` in the
definition of done and in the PR body, never ticked; CI runs them.

`preflight` also copies the pack's knowledge files (planning method, PR steward, review checklists,
the stack notes for the profile's `stacks`), the document templates and the model rules into the
run's artifacts, where the prompts read them.

## Files on the plans branch

Every name is derived from the issue number; nothing is chosen by a model.

```
plans/                      plans_dir (input, else the profile's plans.dir, else plans)
  plans/
    issue-42/
      design.md             written by devflow-refine
      plan.md               written by devflow-plan: the implementation plan and its manifest
      plan-test.md          written by devflow-plan: the test plan
      before.md             written by devflow-plan: steps before the build, or "No manual steps."
      after.md              written by devflow-plan: steps after the build, or "No manual steps."
  workflows/
    build-issue-42.yaml     written by devflow-plan
```

The branch is `plans_ref` (input, else the profile's `plans.ref`, else `plans`). Every file starts
with front matter (`issue`, `kind`, `title`, `revision`, `design_revision` on the plan files, `run`,
`updated`) that a script writes, and follows its template in `.shared/templates/`. One mechanical
check, `.shared/validate-docs.ts`, verifies the structure, the front matter, the manifest and the
links between the files (every Acceptance item of the design is covered by a test case, every case
by a phase); the step that writes a file and the step that reads it run the same check. Run it by
hand with:

```bash
bun packs/devflow/.shared/validate-docs.ts --issue 42 --ref plans --kinds all
```

Commits carry the trailers `Issue: #42`, `Run: <run id>` and, for a plan, `Design: r<n>`. Pushes
are never forced. Plans published before issue folders (`plans/<slug>/`) stay where they are.

A sixth file, `deviations.md`, never lives on the plans branch: the build writes it on the feature
branch as `plans/issue-42/deviations.md`, next to copies of the five documents, and the PR carries
exactly these six files into the default branch (`plans/issue-42/` there), besides the code.

## The issue comment

Each issue gets one comment, marked `<!-- devflow:issue-42 -->` and edited in place. It holds a
table of the design, the plan (marked **stale** when the design has moved ahead) and the build
(not started, building, PR open, merged, closed, **stopped**), links to every file and to the
build's `deviations.md`, and one **Next** line that says what to do: run `devflow-refine`, review
the design and run `devflow-plan`, review the plan and run the build, read `deviations.md` and
review and merge the PR (or run `devflow-follow-up`), read `deviations.md` and run
`devflow-follow-up #42 "<task>"` after a stopped build, or answer the open question with
`devflow-refine #42: <answer>`. When local CI is red on the PR, the line is
`Local CI is red: run devflow-follow-up #57 "fix local CI: <job>"`. Proposed rulings from the design are listed for a person to copy into
`.archon/devflow/policy/rulings.md` (workflows read that file; only people edit it). A comment is
written only after the files are pushed, so a failed comment write loses nothing.

## devflow-refine, step by step

1. **Resolve**: the issue comes from a number, `#42`, an issue URL, a plan or design URL, or
   `issue-42`. A closed issue, or one whose build has started (its feature branch is on origin, a
   `Plan-Phase: issue-42/` commit is on the main branch, or its PR was merged), is refused.
2. **Research** (`@devflow-planner`, else the large tier): reads the issue as data, the existing
   design, the profile's docs and ADRs, the code and `rulings.md`, and searches related issues and
   PRs. A question is asked only when no document, ruling or code settles it, two documents
   disagree, it changes a shipped contract, or the plan would deliver less than the issue asks;
   everything else is decided and recorded as an assumption.
3. **Round 1**: up to 5 questions in one pause. Answer `ok` to take every recommendation, or by
   number (`1: b, 2: ok`). `stop` cancels with nothing published.
4. **Round 2**, only when an answer opened a blocking question: up to 3 more. There is no third
   round.
5. **Write and check**: `design.md` is written from its template (`@devflow-planner`, else the
   medium tier), stamped and checked with `validate-docs`; any error fails the run with every error
   listed. The started check runs again, then the design is pushed and the issue comment updated.
6. **The pause**: `plan` runs the plan block now and publishes `build-issue-42`; `revise` starts
   another pass with your note as the change request (revision 2, a new Revision log line);
   `finish` ends with the design published. A run allows at most 5 revisions; the last pause offers
   no revise.

## devflow-plan, step by step

1. **Resolve and load**: it refuses an issue without a design (`Not planned: issue #42 has no
   design. Run: archon workflow run <pack>:devflow-refine "#42"`), a closed or started one, and a
   `design.md` that does not validate (every error listed: fix it on the plans branch and rerun).
2. **Draft** (`@devflow-planner`, else the medium tier): `plan.md`, `plan-test.md`, `before.md` and
   `after.md`, each from its template. Every design decision is binding. Each implementation phase
   gets a paired `<id>-tests` phase, and a final `verify` phase runs the whole test plan. Each phase
   gets the smallest model tier that can do it, and the plan a final-review tier (`model-rules.md`).
   The feature branch carries `issue-42` and stays the same on a re-plan.
3. **Test**, up to two fix rounds: `validate-docs` on the four files with the design, the manifest
   validator, a dry run of the rendered `build-issue-42` with stubbed children, and a fresh reviewer
   (`@devflow-reviewer`, else the large tier) who checks every phase against the code and every
   design requirement against a phase. Errors go back to the planner. After the last round only
   review findings may remain; they are published under "Unresolved validation findings" with a
   warning. Anything else fails the run: an invalid plan is never published.
4. **Publish**: the four files and `workflows/build-issue-42.yaml` in one commit, checked again
   with `validate-docs` at that commit, then the issue comment. `published.md` in the run's
   artifacts says how to load and start the build. The run never runs `archon workflow sync`; you
   do.
5. **A gap the design leaves**: when the planner cannot decide it safely, the run ends
   `planned: false, needs_refine: true`, the question goes on the issue comment, and nothing is
   committed. Answer it with `devflow-refine "#42: <answer>"`.

## The build workflow `build-issue-<n>`

The build is unattended: after `start` it has no pause, approval, select or cancel. Claude decides
what the plan leaves open and records it.

1. **start** (`mod-devflow-start`) validates the issue's documents on the plans branch with the
   same `validate-docs` check `devflow-plan` ran, refuses when the feature branch already exists (in
   another worktree or on origin: use `devflow-follow-up`), creates it from the default branch, and
   commits and pushes a stub `deviations.md`. These refusals change nothing.
2. **before** (only when `before.md` has steps) checks each step's `Done when:` line with read-only
   commands and records met, unmet or unknown. It never blocks.
3. **Phases** run up to three at a time, each as a `mod-devflow-phase` child run in its own worktree
   on the phase's model tier; every implementation phase has its `<id>-tests` phase and a final
   `verify` phase runs the whole test plan. A phase that cannot finish (blocked, red checks after
   the last fix round) reports **stuck** instead of failing the run; a phase whose dependency is not
   done is **skipped**; independent phases carry on.
4. **merge-<k>** merges the done phases of each wave by SHA with a `Plan-Phase: issue-<n>/<phase>`
   trailer. A conflict is aborted and recorded; the phase's head is kept as
   `<branch>-partial-<phase>`.
5. **wrap** (`mod-devflow-wrap`) always runs: it writes `deviations.md` from the phases' outcomes,
   commits this issue's six files under `plans/issue-<n>/` (nothing else: no other issue, no
   `workflows/`, no worktree), and pushes the branch and every `-partial-` ref (never forced; a
   rejected push goes to `<branch>-stopped-<run>`).
6. **deliver**, only when every phase is done and the push went through, runs the fast-check fixes,
   the build gate and the shared tail: review on the plan's final-review tier, fixes, the
   definition of done and local CI (`mod-devflow-dod`), one PR with `Closes #<n>`, a Traceability
   section (design and plan with their revisions) and a Deviations section, the final
   `deviations.md` committed into the PR, then a watch every 10 minutes that hands conflicts, red
   checks and review threads to a steward session until a person merges or closes the PR.
7. **wrap-final** (`mod-devflow-wrap`, stage final) runs whatever deliver did: a deliver that
   failed or opened no PR (a red review, a red definition of done, a `gh` error) is recorded under
   `Review and CI`, and `deviations.md` is committed and pushed again. wrap, deliver and wrap-final
   share the build's checkout, so they run one after another.
8. **end** fails the run when the build is not complete (`build-issue-<n> is not complete: see
   deviations.md (<url>)`), after wrap-final has committed and pushed.

Guarantee: once `start` has created the branch, every ending passes through `wrap` and then
`wrap-final`, so the branch carries `deviations.md`. Its limits: a refusal before `start` creates
the branch leaves nothing (and changes nothing), and a killed run (host crash, `archon workflow
cancel`, a timeout of the whole run) cannot run `wrap`; the stub `deviations.md` committed by `start` is then on the branch, and
`devflow-follow-up` finishes the job.

The issue comment moves from building to PR open to merged or closed, or to stopped.

Concurrent phase children each fetch tags in worktrees of one repository, so one can fail with
"cannot lock ref". Resume the parent run: Archon re-drives the failed child.

## deviations.md

Written only by a script (`write-deviations.ts`, from `templates/deviations.md`) from the phases'
typed outcomes, so its structure is fixed and `validate-docs` checks it: Outcome (completed,
stopped or running; phase counts; branch; PR), Stuck and skipped phases (with the partial
branches), Deviations from design and plan (`V<n>`), Decisions taken (`K<n>`, everything decided
where the design and the plan were silent), Tests (each `T<n>` case of `plan-test.md` per phase:
pass, fail or not run), Before steps (met, unmet or unknown with the evidence), After steps (always
yours: see `after.md`), Review and CI (findings fixed and left, checks, local CI), and Follow-ups
(`F<n>`, one per `devflow-follow-up` run). Read it before you review the PR.

## Local CI (`verify.ci_local`)

After the definition of done, `mod-devflow-dod` runs the repository's own CI jobs in the worktree
with `ci-local.ts` (mechanical, no AI). By default (`jobs: auto`) that is every job of
`.github/workflows/*.yml` that runs on `push` or `pull_request`, on an `ubuntu-*` runner, with no
`services:`, `container:` or job-level `uses:`, whose steps reference no secret or `github.token`,
in a workflow that is not in `ci.dispatchable`. Only the first matrix combination runs; setup and
cache actions are skipped (the run's `setup` prepared the tools); a step needing a missing tool, or
an expression it cannot resolve, skips its job with the reason. Tokens and variables named like
secrets are removed from the environment.

A red result gets at most two `ci-fix` sessions (they fix the code or the tests, never
`.github/workflows/`, never weaken or skip a test), then a final run. Still red: the PR is opened as
a **draft** with a "Local CI failed" section, `deviations.md` records it and the issue comment says
`Local CI is red: run devflow-follow-up #<pr> "fix local CI: <job>"`; the build still counts as
complete. No runnable job is recorded as `skipped`. Configure it with `verify.ci_local`
(`enabled`, `jobs`, `skip_jobs`, `timeout_minutes`, `env`); `bun .shared/ci-local.ts --list` shows
what would run. Every workflow with the shared tail (`devflow-quick`, `devflow-docs`,
`devflow-config`, `devflow-deps`, the audit fix) runs local CI too.

## devflow-follow-up

`devflow-follow-up <pr | issue | deviations.md URL> "<task>"` continues a build after it ended,
unattended. It finds the issue from a PR (its `plans/issue-<n>/` files, else `Closes #<n>`), an
issue, or a `deviations.md` URL. With an open PR, or a stopped build without one, it continues the
build's branch; after a merged or closed PR it starts `followup/issue-<n>-<k>` from the default
branch. One task phase (`f<k>`) does the work in that checkout, with the PR's review comments as
untrusted data. With an open PR, the definition of done and local CI run again; a draft opened for
red local CI is marked ready once the definition of done and local CI are green (or local CI has no
runnable job), and a marked comment on the PR summarises the
follow-ups. Without a PR, a done task is delivered as a new PR. Every ending appends
`### F<k> (<date>, run <id>): <task> → done|stuck` with its decisions to `deviations.md`, commits
and pushes it; a stuck task then ends the run red. Documents that no longer validate are recorded
as deviations, never a refusal.

## devflow-init

`devflow-init ["<hint>"]` prepares a repository and can be re-run any time. A scan (no AI) reads
the existing profile, or the legacy profile of the retired plugin (converted, see "Migrating from
the toolkit" below), the default branch, the merge settings, branch names,
docs, the commands in `package.json`, `Makefile`, `pyproject.toml`, `go.mod`, `Package.swift` and
`scripts/test*`, the stacks, the dispatchable workflows and the jobs local CI would run. An agent
drafts the profile from it, marks where each value came from (existing, detected, default), keeps
existing values unless the hint changes them, never invents a command, and asks at most two rounds
of questions, only where a required key stays undecidable, two sources disagree, a dispatchable
workflow needs its `use_when`, or project policy fits no key. Reply `ok`, answer by number, or write
a change such as `verify.dod: make test-all`; `stop` cancels with nothing written.

Then `write-profile` validates and writes `.devflow/devflow.yaml` (an invalid draft fails with every
error; rerun with a hint), `scaffold-repo` creates only what is missing
(`.archon/devflow/policy/rulings.md` with its entry format, the plans source in
`.archon/config.yaml`, `.archon/worktrees/` in `.gitignore`) and removes the legacy profile,
`doctor` checks `gh`, `origin`, `python3` with PyYAML, `bun`, the profile, the first word of every
check command, the dispatchable workflow files, the plans branch, the Archon config, the installed
pack and the local CI jobs (a missing `archon`, `gh`, `python3`, `git` or `bun` is a warn row that
says to install it; the doctor never fails the run), and `publish-init` creates the plans branch when origin lacks it and
opens one PR on `chore/devflow-init` (the profile with its sources, the doctor table, a checklist
of the retired plugin's hook leftovers to remove by hand, the next commands). Nothing changed: no branch, no PR.

## Profile

`.devflow/devflow.yaml` is the only place a project's facts live. Every run validates it with
`.shared/validate-profile.py` against `.shared/profile.schema.json` and reads the resolved result
from `$ARTIFACTS_DIR/profile.json`. A missing required key stops the run with its name; an unknown
key is an error; a missing optional key means "not used". Every key is described in
`.shared/knowledge/profile-reference.md`. This repository's own profile is an example:

```yaml
version: 1                       # required, always 1
project:
  name: archon-work
docs:
  must_read: [README.md]         # read by the planner, every worker and the reviewer
git:
  main_branch: main
  branch_pattern: <type>/<kebab-case>
  branch_types: [feat, fix, docs, chore]
  merge_style: merge-commit
verify:
  fast:                          # every implementation step runs these
    - bash -n bootstrap.sh
  dod:                           # the definition of done, before the PR
    - scripts/test-devflow-pack.sh
stacks: []                       # python, go, swift, ipados: the stack notes the agents read
plans:                           # optional: where the plans branch is
  ref: plans
  dir: plans
```

Optional keys also include `docs.adr_dir`, `docs.adr_index`, `docs.adr_bar`, `docs.changelog`,
`verify.dod_conditional`, `verify.dod_manual`, `verify.dod_doc`, `verify.ci_local`,
`ci.dispatchable` and `project_steward`.

## Models

The stage agents use two model aliases, each falling back to its tier when your Archon config
does not define it:

| Alias | Nodes | Fallback |
|---|---|---|
| `@devflow-planner` | `research`, `research-2` | `large` |
| `@devflow-planner` | `write-design`, `draft-plan` | `medium` |
| `@devflow-reviewer` | `plan-review` | `large` |

```bash
archon ai alias set @devflow-planner <provider> <model>
archon ai alias set @devflow-reviewer <provider> <model>
```

Every other node keeps its tier; the generated build uses the tier the plan gives each phase.

## Enable plan workflows in a project

This needs Archon 0.13.4 or later from `tkcs-lab/Archon` (`bootstrap.sh`'s default `ARCHON_REPO`) for `extraWorkflowSources`; upstream `coleam00/Archon` does not have it.

`devflow-init` does both steps: it creates the plans branch and adds the source to
`.archon/config.yaml` in its PR. By hand:

1. Run `devflow-refine` once in the project, so the `plans` branch exists.
2. On the default branch, add this to `.archon/config.yaml`, then run `archon workflow sync`:

   ```yaml
   extraWorkflowSources:
     - ref: plans
       path: plans
   ```

**Warning:** a configured source that was never synced fails every run in that project, so add the
config only after the branch exists. The `plans` branch is as public as the repository: keep
confidential work to `devflow-audit`, which never publishes.

Limits: a folder project has no worktree isolation, so the parallel phases need a git repository.
The generated workflow uses the pack the plan run was started from; pass `--input pack=<owner>/devflow` to target another installed pack.

## Migrating from the toolkit

The pack no longer uses the claude-toolkit plugin, its commands, skills or SessionStart hook: its
validators, schema and knowledge live in `.shared/`. To migrate a project, run `devflow-init`: it
converts `.claude/toolkit.yaml` to `.devflow/devflow.yaml` (adds `version: 1`, drops `toolkit`,
`models` and `docs.plan_dir`, which the validator only warns about), deletes the old file in the
same PR and lists the hook leftovers (`.claude/settings.json` entries, `.claude/hooks/devflow.sh`)
for you to remove; remove the plugin and its hook from the machines too. `devflow-plan` and
`devflow-refine` keep their names with the new behaviour. Plans published before as
`plans/<slug>/` with a `devflow-run-<slug>` workflow stay on the plans branch untouched and remain
runnable.

## The other workflows

- **devflow-quick** writes a short `work.md` instead of a plan, makes the edit in one session with
  `verify.fast`, then runs the tail. Its scoping agent refuses a change that needs a design decision,
  touches authentication, authorization, secrets or other security controls, meets the profile's ADR
  bar, adds an outside integration or bumps a dependency, and says to use `devflow-refine`.
- **devflow-docs** has a reviewer apply the pack's `docs-review` checklist and measure (website build if
  there is one, documented commands, links, changelog coverage). The fixes become `work.md`; what is a
  product or wording decision goes to the PR's "Needs a person" section instead of into edits.
- **devflow-audit** runs an auditor, then a fresh verifier that tries to disprove every finding and
  decides fix, not doing or needs a decision, then includes `mod-devflow-audit-fix`, a confidential
  one-run plan and implementation, with the surviving findings as the work. The findings never leave the run's artifacts: no issue, and the PR names the class of
  fix, not how to attack it.
- **devflow-config** snapshots the repository's configuration through the GitHub API (read-only, with
  the agent's token; each endpoint records whether this token could read it, and a 404 for a non-admin
  token counts as unknown, not off), then a reviewer compares it with the repo's documented intent, its
  workflow files, its `.archon/config.yaml` and, if `reference` is given, that repository. The review
  is read-only. File fixes (workflow files, which need the `workflow` scope on the agent's token,
  `dependabot.yml`, `CODEOWNERS`, `SECURITY.md`, `.archon/config.yaml`) go through a PR and the shared
  tail. Settings gaps are listed in `config-review.md` for the admin user's `gh-baseline` (root README
  §3 "Admin GitHub identity").
- **devflow-deps** reads the open Dependabot PRs and alerts, reviews each PR as a supply-chain change
  (version jump, new transitive packages, install scripts, release notes), then repairs the chosen PRs
  one at a time on their own branches: checks run, locks regenerated with the repo's tool, fixes
  pushed to the Dependabot branch, CI read back, at most two attempts each. Alerts no PR covers are
  fixed on a new branch through the shared tail. It never merges and never dismisses an alert.

## Prove changes

```bash
scripts/test-devflow-pack.sh
scripts/test-render-run.sh
scripts/test-devflow-validators.sh
scripts/test-devflow-shared.sh            # or only some parts: scripts/test-devflow-shared.sh 1 4 11
```

- `test-devflow-pack.sh` loads the pack as a project pack in a scratch repository, runs `archon
  validate workflows` and replays every fixture with `archon workflow test`. Fixtures named for a
  red path (`review-never-clears`, `dod-stays-red`, `plan-test-never-clears`, `not-small`, ...)
  must stay red; the ones that execute a script set `exec-code: true`. It then runs
  `scripts/check-no-toolkit.sh`, which fails when the retired toolkit's names appear outside the
  migration's allow-list (the names and the allow-list are in the script).
- `test-render-run.sh` tests the build renderer (`render-run.ts`), the plan block's `render-run`,
  `test-plan` and `check-plan` scripts, and `load-plan.ts`.
- `test-devflow-validators.sh` runs `validate-profile.py` and `validate-manifest.py` on the
  fixtures in `scripts/fixtures/validators/`, and this repository's own profile.
- `test-devflow-shared.sh` runs the hermetic parts in `scripts/shared-tests/` (scratch repositories,
  a local bare origin, a stub `gh`, no network): 1 resolve-input, 2 front matter, 4 the issue
  comment, the attention table and the trace, 5 the plans branch, 6 publishing a design and a plan,
  7 the render tests, 8 the build's start, merge and wrap scripts (deviations.md, staging, pushes),
  9 resolve-followup, 10 devflow-init's scripts, 11 validate-docs and the templates against
  `scripts/fixtures/docs/`, 12 local CI.

Adapted from the PrivacyFence pack ([privacyfence/privacyfence `.archon/`](https://github.com/privacyfence/privacyfence/tree/chore/archon-devflow-workflow/.archon)).
Its `devflow-release` is not here: it drives that project's own release script and build workflows.
